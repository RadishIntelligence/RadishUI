# RadishUI 整体规划

本文维护项目长期目标、范围、阶段与出口。[专题地图](topics.md)组织大专题与子专题，[当前规划](current.md)维护当前顺位、阻塞与停止线；详细任务状态在各子专题，执行事实在开发记录。

## 目标与非目标

让家族产品通过消费共同设计基础和真实组件，减少重复解释视觉意图与重复实现。交付包含语义 token、平台组件、可运行页面范例，以及可复验的视觉和交互基准。共享改进在产品明确升级后生效，不自动改写各产品。

React 与 Flutter 分别实现，共享设计语义与关键状态；egui、自绘环境和 Godot 按真实需求单独考虑。产品业务、接口、身份权限、路由、领域状态与游戏专有视觉不进入通用底层。独立展示站由本仓维护，RadishX 提供家族介绍与入口。

## 阶段与完成条件

阶段是交付顺序，大专题是能力归属；同一阶段可涉及多个大专题，不另建重复任务清单。以下不承诺日期、发行版本、许可、未确认 API 或产品接入范围。

| 阶段 | 结果与出口 | 主要来源 |
| --- | --- | --- |
| P0 工程基线 | workspace、token 管线、首个组件、真实展示和部署路径能构建、审阅与复验；规划功能不算实现 | [初始化验收](../features/bootstrap.md)、[工程与交付](topics.md#engineering) |
| P1 视觉基准 | 从真实需求确认代表页面、通用状态与设计来源；萝卜SAMA确认后才成为正式视觉基准 | [视觉基础](topics.md#foundations)、[范例与接入](topics.md#examples) |
| P2 React 有限复用 | 确认首批组件，在有限产品页面实际消费；记录版本、迁移、例外、视觉与交互结果，比较实际收益与接入成本后决定是否继续采用；单一试点不代表全家族完成 | [跨平台组件](topics.md#components)、[范例与接入](topics.md#examples) |
| P3 Flutter 验证 | 确认试点和产物格式后验证同一设计语义，明确平台差异与真实支持范围 | [跨平台组件](topics.md#components) |
| P4 正式发行 | 先确认许可证、包名、构建与导出、支持矩阵、回滚及发布门禁；版本策略已定，见[版本策略](../development/versioning.md) | [工程与交付](topics.md#engineering)、[设计系统契约](../development/design-system.md#版本产品采用与回滚) |

## 全局验收

- 工程成立：正式检查、构建、生成物与远端门禁分别有真实结果；模板不能代替已启用设置。
- 视觉成立：组件和代表页面在明暗、桌面 / 窄屏及关键状态下经过确认，不能只凭 token 相同或组件陈列判断家族一致性。
- 复用成立：产品实际使用共享组件或明确平台产物，有采用版本和升级 / 回滚记录；只是阅读文档不算接入。
- 平台成立：按平台、运行时和版本逐项验证，React 通过不推断 Flutter 或其他 React 版本通过。

只完成 P0 不代表整个设计系统完成；一组组件验收不代表所有页面、平台和产品已采用。阶段出口与子专题验收共同判断，不按文档数、任务勾选数或构建成功次数推算完成率。

## 规划维护

新增能力先在专题地图确定一个主要归属，再沿对应子专题定义用户场景、边界、依赖、实施与验收。远期内容只登记范围和启动条件，不创建空专题或自动扩展执行授权。跨专题改动引用原任务和证据，不维护第二套进度。
