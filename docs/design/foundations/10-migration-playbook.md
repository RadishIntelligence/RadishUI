# 10 版本、产品采用与回滚

文档集中、视觉批准、token 升级、组件采用和发行分别验收。先在 RadishUI 内确认共享设计，再独立评估产品采用范围；资料研究本身不要求来源仓迁移或接入。

变更 token 名称、语义、默认视觉或公共 API 前说明消费位置、兼容影响与迁移。旧 family-ui 与当前工程存在同名不同义项；保留固定来源，明确逐项映射，不能同时加载或以链接替代构建需要的本地文件。

产品正式决定采用后，再建立薄适配说明，只记录：

- 采用的 RadishUI 固定版本 / 提交、Profile 与主题映射；
- 真实使用的组件、页面及平台，明确未采用部分；
- 必要产品例外、原因、范围和退出条件；
- 产品设计源、业务合同、实现映射与验收链接；
- 升级验证、回滚版本与负责人。

产品正式切换通用资料后，原则和参考索引链接到确定版本的 RadishUI；产品历史记录保留原文，通过旧路径追溯。正式切换前保留产品当前文档与素材，不提前删除副本或替换入口。没有发布的新链接不能冒充已生效引用。

获单独授权后的迁移顺序：确认产品与资料范围 → 目标到位并校验 → 验证采用 → 更新旧入口 → 按确认范围移除重复副本。删除来源文件必须在该次授权范围内，不从本仓研究或设计批准自动推导。Git 历史不重写，普通修复 / revert 可恢复；私有资料不因迁移获得新的对外许可。

采用方升级分别完成真实验证，先选择一个有限页面试点，再决定是否扩展。具体产品与顺位由后续采用任务确认，不在通用原则中预设。
