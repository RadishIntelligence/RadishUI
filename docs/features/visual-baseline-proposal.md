# F-02：视觉基准、代表页与资料归集方案

日期：2026-11-03（Asia/Shanghai）。方案状态：草案，待萝卜SAMA确认；执行状态：现状梳理与方案已完成，资料迁移、视觉定稿和组件实现未开始。

主要归属：[F：视觉基础](../planning/topics.md#foundations)，协同 C 组件、E 范例与采用、G 工程交付。承接[整体规划 P1 / P2](../planning/roadmap.md)，本轮只给方案，不改变既有 token、API、依赖、产品实现或远端状态。

## 1. 建议结论

1. RadishUI 接管家族通用设计规范、通用参考索引、获准公开的自有基准和共享组件；RadishX 回归官网与入口职责。
2. 先确立 Workbench 工作面：近白暖调、灰玉识别、墨蓝操作、清楚主次和连续内容；Brand 与 Content 共享基础、分别编排。Catalyst 的游戏视觉保持独立。
3. 先审三个可运行代表页：资源列表 / 详情、外观与偏好设置、文档阅读 / 编辑；由页面需求倒推组件，避免先堆组件陈列墙。
4. 通用资料集中，产品保留薄适配说明；外部受限截图、私人材料和产品专有合同分别处理，不将“集中”理解为直接搬入公开仓库。
5. 文档 / 参考迁移与运行时迁移分开。旧 family-ui 存在同名 token 与当前 RadishUI 含义不一致的情况，不能用旧 CSS 覆盖当前实现。

### 三个直接影响方案的发现

- RadishX 源码 / 参考 CSS、Radish 的 family-ui CSS、Mind 的 token CSS 字节一致；三份参考 JSON 也一致。已有共同 token 仍无法保证组件、页面结构和密度一致。
- Mind 参考映射记录了米色雾感、圆角小卡、等权信息块和无职责外框被人工退回的过程，后续采用连续窗格、明确主对象和主次数据关系。应继承这些具体判断，不能退回“统一米色 + 卡片”的做法。
- 相同截图在 Flow 与其他仓库中出现产品命名不一致。例如 Flow 名为 `onepanel-file-manager-table.png` 的文件，实际是 Discourse 管理活动页，字节与 Radish / Mind 对应图相同。迁移须按内容和出处纠正元数据，不按文件名机械归类。

## 3. 视觉基准候选

建议以“安静、清晰、温润的现代工作面”为首版目标。保留家族身份，减少整屏偏黄、装饰纹理和平均分布的小卡。以下是待审设计参数，不是已经冻结的 token 或跨产品强制数值。

| 维度 | 候选规则 | 首次重点核验 |
| --- | --- | --- |
| 表面 | 近白暖中性主内容，轻微色差区分导航 / 背景；深色用暖墨层次 | 白色层次、长时间阅读、明暗文字与边界辨识 |
| 品牌与操作 | 灰玉表达识别，墨蓝表达常规主操作；状态色独立 | 品牌 / action / danger 不混用，暗色实底前景可读 |
| 排版 | 工作面系统无衬线；界面正文参考 14px、阅读 16px、主标题 24–28px；代码 / 数字按需等宽 | 中文与长英文、数值对齐、大字号、页面主次 |
| 空间 | 4px 基础网格；桌面控件参考 36 / 40px，触控命中区至少 44px | 密度来自任务，不能缩小到难读或用弹性行高填空 |
| 形态 | 控件约 6–8px 圆角，面板约 8–12px；弱边界，浮层才适度抬升 | 避免全页硬方框，也避免卡片套卡片和外圈展示窗口 |
| 结构 | 单一主对象；列表 / 正文连续组织，辅助栏按需出现；顶栏克制 | 不默认加入 KPI 卡带、第二条导航或装饰性副标题 |
| 状态 | success / warning / danger / info / neutral 加文字或图标；选择态独立 | 错误、只读、加载、未保存与当前选中不能混为一种颜色 |

Profile 建议：Workbench 首先建立；Content 共享组件但调整行宽、阅读字号与内容节奏；Brand 允许展示性排版和有限品牌表现。Content 是本提案拟明确的布局分类，不冒充旧 family-ui 已有 Profile。Game 只共享必要的语义和可读性原则，不统一游戏画面。

参考的分工：ref-05 用于设置分组和中文密度；ref-27 用于连续窗格和列表 / 详情关系；ref-01 用于表格扫描与行操作；ref-20 用于暗色表面层次；ref-25 用于字段和浮层关系。仅吸收这些关系，不沿用截图里的 KPI、原配色、品牌、装饰背景或表面组合。Nexus 的已导出基准是家族转译候选，也需要从产品页面重新抽象。

### token 兼容问题先登记，出稿后决策

| 同名语义 | 旧 family-ui 参考 | 当前 RadishUI 工程预览 |
| --- | --- | --- |
| `--rd-space-6` | 32px | 24px |
| `--rd-space-8` | 64px | 32px |
| `--rd-bg-app`（light） | `#f4efe6` | `#f4f3ee` |
| `--rd-state-danger`（light） | `#c3564d` | `#a93b36` |

品牌 `#5d6c57` 和操作 `#435c74` 相同，也不能据此判断整套兼容。先建立名称 / 角色 / 值 / 消费位置的差异表，区分语义冲突与视觉取值调整；视觉候选获批后确定规范化命名、版本和迁移映射。不能同时加载两套同名不同义 CSS，不能用迁移文档替代产品实际升级。

## 4. 三个代表页面

共享一套工作面骨架，使用重新构造的中文 / 英文和长内容，不带产品 API、权限或路由。优先用完整页面判断设计，再提炼公共 API。

| 页面 | 主要结构与动作 | 必须出现的状态 | 候选经验来源 |
| --- | --- | --- | --- |
| R1 资源列表与详情 | 单导航、轻页头、搜索 / 筛选、连续列表或轻表格、当前行与详情；窄屏进入单一详情 | 初次加载、空结果、失败 / 重试、选中、只读、长名称 | Mind 工作面、Radish Console、ref-01 / 27 |
| R2 外观与偏好设置 | 分类导航、连续表单分组、主题 / 偏好、主次动作与危险区分隔 | 字段错误、禁用原因、保存中 / 成功 / 失败、未保存离开 | AFFiNE / Codex 设置参考、Nexus、原生设置经验 |
| R3 文档阅读与编辑 | 导航、标题与元信息、受控阅读宽度、按需属性区、明确编辑 / 保存 | 长中文 / 代码、只读、未保存、失败保留输入、离开确认 | Nexus 已导出阅读 / 编辑稿、Radish 内容阅读 |

R3 首批只验证通用排版与简单编辑表面，不因此引入 Markdown 编辑器、块编辑、实时协作或版本冲突算法。R1 轻表格不因此增加服务器分页、虚拟化或全功能 DataGrid。

首轮各页画桌面 / 窄屏的明暗默认状态，共 12 个主要组合；错误、加载、确认等通过组件或局部状态表达，不为每个状态复制完整页面。实现后再检查中间宽度、键盘、缩放、长内容、滚动和焦点；截图通过不代替功能与可访问性判断。

## 5. 首批组件与提取方式

按代表页实际需要分两段实施，表中是候选组件范围，不代表公共 API 已批准。

| 批次 | 组件 | 首批边界 |
| --- | --- | --- |
| A：操作 | Button、IconButton | 层级、尺寸、loading / disabled、图标名称与焦点；扩展当前真实 Button |
| A：字段 | Input、Textarea、FormField、Select | label、hint、error、只读、长度与键盘；Select 先验证原生选择能力 |
| A：选择与定位 | Checkbox、Switch、Tabs、StatusBadge | 受控状态、标签、键盘语义、选择与状态分离 |
| B：浮层 | Dialog、Drawer、Menu | 焦点进入 / 约束 / 恢复、关闭、滚动锁与嵌套；先评估可靠交互基础，不机械复制现有实现 |
| B：反馈 | InlineAlert、Toast、Tooltip | 可读反馈、自动消失边界、非颜色表达；不得用 Tooltip 承载唯一必要说明 |

A 为 10 个组件，B 为 6 个；先做 A，再按 R1 / R2 的真实需要接 B，不同时铺开全部能力。AppShell、PageHeader、列表 / 详情、设置分组和轻表格先作为组合范例维护，避免过早冻结大而全的布局 API。Skeleton、EmptyState、Popover、完整表格和复杂编辑器在真实复用需求明确后补，不为凑齐控件清单提前建框架。

`@radish/ui` 的 Button / Input / Select / BottomSheet 等是提取候选，不能整包引入：其包依赖包含 `@radish/http`、Ant Design、图表和编辑相关能力，根入口还导出 API。已读 Modal 有 Escape 与滚动处理，但未见完整 dialog 语义及焦点管理；BottomSheet 有更完整的焦点处理，可参考相应经验。此为源码检查，不是完整无障碍审计或“可直接复制”的结论。

React 首先验证现有 React 19 范围；Ink 的 React 18 另建消费兼容证据，不预先承诺。Flutter 下一步先验证主题与按钮 / 字段 / 反馈的语义对应，参考 Radish Native 的 ThemeExtension / ThemeData 经验，不迁入主题权益、业务网关或平台 bridge。

## 6. 资料集中与兄弟仓库的最终形态

### 集中维护什么

RadishUI 成为通用设计资料的正式来源，建议未来归位如下；这是目录方案，本轮不创建空目录或拷贝素材：

```text
docs/design/foundations/     家族原则、颜色、排版、密度、状态、动效
docs/design/components/     组件语义、状态、可访问性和采用边界
docs/design/patterns/       代表页与组合模式
docs/design/references/     可公开参考索引、学习点、出处与采用说明
designs/                    通过 Pencil 建立的 RadishUI 可编辑通用基准
assets/design-baselines/    获准公开、合成数据的自有验收基准
```

F-02 继续维护本次迁移 / 定稿任务与进度，设计正文在上述稳定专题，E-01 继续维护展示实现，不在多处重复同一待办。

### 不能将所有文件直接搬进公开仓库

| 材料 | 处理方案 |
| --- | --- |
| 家族通用原创规范、通用 token 参考、抽象的布局经验 | 确认权属与采用许可后迁入 RadishUI；保留来源仓库、原路径、提交与版本历史，整合冲突后统一维护 |
| 外部产品截图 | 现有 family-ui 明确仅供内部观察、禁止对外分发 / 再托管，部分还可见真实账号信息；不新增到公开 RadishUI。集中公开的出处和学习点；允许内部保存的原图统一放仓库外的受控资料库，授权人员按受控索引访问 |
| 自有设计稿与合成数据预览 | 逐项确认归属、数据和许可后，可迁通用部分；`.pen` 只通过 Pencil 读取、提取与验证，核对图片 / 字体依赖，不能文本搬改 |

建议默认采用“公开 RadishUI 维护规范 / 原创基准，受限参考材料集中在仓库外私有资料库”的安排；位置与访问方式在执行前确认。既要全部原图存 Git 又要保持同一仓库公开，与现有材料约束不相容，不能靠忽略目录后强制提交解决。
